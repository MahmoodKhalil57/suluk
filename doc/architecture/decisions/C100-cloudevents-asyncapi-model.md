# C100 — A typed CloudEvents 1.0.2 + AsyncAPI 3.x model in `@suluk/core` (the event-architecture source-of-truth)

> **Provenance.** A Suluk *candidate* decision (codename `asl-ojs`), authored by the single contributor, grounded in
> burhan/daftar/mizan — **not** a Moonwalk SIG decision. Operator-driven (2026-07-04). The async twin of
> [C099](C099-typed-json-schema-model.md); reference models: the `cloudevents` npm package (`CloudEventV1<T>`) +
> `@scalar/types` `asyncapi/3.1`. NON-normative per [C018].

**Status:** BUILT + VERIFIED + LIVE-ADOPTED (the CloudEvents envelope builder + the AsyncAPI document types were hoisted
into `@suluk/core`; `@suluk/hono`'s `emitAsyncApi` now derives from them, **byte-identically** — its 8 asyncapi tests stay
green; the whole ~30-package `@suluk/core` graph typechecks clean). NOT published. Confidence ceiling **0.72** — the
hoist + adoption are executable-witnessed @≥0.85, but real registry apps don't yet *populate* the event facets end-to-end,
and it's unpublished.

## Context

Operator: *"can we also use npm cloudEvents to improve our core type for apis with event architecture the same way we
used json schema and typebox"* + *"consider `@scalar/types` asyncapi/3.1."* This is the exact analog of C099: Suluk already
has an event surface — `webhooks` (C018), `x-suluk-jobs` (C025), per-op `x-suluk-store.invalidates` (C037) — and
`@suluk/hono`'s `emitAsyncApi` already projects it to **AsyncAPI 3.0 + CloudEvents 1.0.2**. But the CloudEvents envelope was
an **ad-hoc inline JSON Schema** (`cloudEvent()`), and the AsyncAPI document types were a **hand-rolled local subset** — both
buried in a generator, neither a typed source-of-truth in core. Precisely the pre-C099 situation, one layer over.

The C099 forks carry over unchanged (the operator's "the same way"): **pure types, no runtime dependency** (reference the
standard, don't depend — the `cloudevents` npm 3.x line pulls a fair bit of surface; core stays dep-light); **type-only**
(the async projection stays generated by `emitAsyncApi`); and — the one genuinely new fork — **projection, not normative**:
the async surface is explicitly *"a separate projection, NOT normative to the OpenAPI contract"* and C018 held async
constructs out of normative scope, so these types are a non-normative **emit target**, exactly as they are used today.

## Decision

Hoist the event-architecture model into `@suluk/core`, and rewire `@suluk/hono` to consume it.

**Single-file follow-up.** The model was first landed in a new `src/events.ts`, mirroring nothing in particular —
C099's Schema Object model lives directly in `src/types.ts`, no separate file. The operator caught the inconsistency
("why does events get its own file when schema didn't — can't core be one document?") and it's correct: `@suluk/core`'s
`index.ts` already flattens every export into one flat namespace regardless of internal file layout, so a second
source file bought nothing and only made it look like two documents to maintain. Consolidated into `src/types.ts`
(a clearly-marked, self-contained section at the end) — `events.ts` deleted. One file, one source of truth, matching
C099's precedent exactly.

**CloudEvents 1.0.2 (the envelope).** `CloudEventV1<T>` mirrors the `cloudevents` npm package field-for-field via the same
three-layer shape (`CloudEventV1OptionalAttributes<T>` → `+ source/type` → `+ id/specversion`, with the extension index
signature), so a runtime `cloudevents` event is structurally assignable — with **no dependency**. Plus the content-mode
vocabulary (`CloudEventContentMode`, the `application/cloudevents+json` / `-batch+json` media types, the `ce-` binary-mode
header prefix), an `isCloudEvent` guard, and **`cloudEventEnvelopeSchema()`** — the envelope's JSON-Schema face, built on the
**C099 typed `ObjectSchema`** (the C099↔C100 bridge: the async envelope is now expressed with the sync Schema model).

**AsyncAPI 3.x (the document).** `AsyncApiDocument`/`Info`/`Channel`/`Operation`/`Message`/`Parameter`/`CorrelationId`/
`Components` — informed by `@scalar/types` `asyncapi/3.1`, reusing the C099 `Contact`/`License`/`ExternalDocumentation`/
`Schema`. They are an **emitter** type: `channels`/`operations`/`components` are required because a Suluk-emitted doc always
carries them (Scalar's parse-oriented model has them optional).

**Adoption.** `@suluk/hono`'s `asyncapi.ts` drops its local type block + inline `cloudEvent()`, imports the model + builder
from `@suluk/core`, and **re-exports the four AsyncApi types** so its public API is unchanged. `emitAsyncApi`'s output is
**byte-identical** (the envelope builder reproduces the previous shape exactly; the 8 asyncapi tests assert the exact
envelope and pass). This makes the source-of-truth real, not dead types — the analog of C099's `Schema` being what `zodToV4`
emits.

## Consequences

- The event surface is now a typed source-of-truth in `@suluk/core` (`CloudEventV1<T>` for "what an event instance is",
  `cloudEventEnvelopeSchema` for its doc schema, `AsyncApiDocument` for the projection), still **zero-runtime-dependency**.
- **Non-normative** (C018 upheld): nothing about the normative v4 contract changes; these types describe the async
  *projection*. A future decision could let `webhooks`/jobs *declare* a CloudEvents payload normatively — deliberately not
  taken here.
- `@suluk/hono`'s async types + envelope now have one home; consumers importing them keep working (re-exported).
- **Deferred:** publish `@suluk/core`; real registry apps populating the event facets end-to-end; CloudEvents HTTP binding
  helpers (binary-mode header (de)serialization) beyond the prefix constant; typing `webhooks`/jobs to carry a
  `CloudEventV1` payload normatively.

Pairs with `plan/facts/0cloudevents-asyncapi-model.bn`. Builds on C099.
