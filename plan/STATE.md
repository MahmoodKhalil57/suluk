## ✓ C118 — `params`/`InputOf`/`passthrough` (a real, bubbling path-param schema) + a genuine `sulukFmt` soundness fix

Operator (direct follow-on to C117), naming 3 concrete violations: a hand-written `provide` helper per route
file; `z.infer<typeof CreateReq>` imported and written manually in a controller instead of bubbling from the
model through the service; and, **most importantly**, a query function declaring raw `id: string` instead of a
real zod schema — *"ideally directly inferred from the zod-drizzle schema declaration itself, so we can have it
bubble up through service to route and merge types depending on the pipeline so we never have to maintain a
separate source of truth."* ADR [C118](../doc/architecture/decisions/C118-params-inputof-sulukfmt-soundness.md);
`plan/facts/0params-inputof-sulukfmt-soundness.bn` (@≥0.85-0.9; burhan-converge clean, 91 files/568 claims).

- **`params?: z.ZodType<Params>`** added to `sulukFn`/`RequestSlice` (mirrors `body`) and to `queryOne`/
  `queryMany`/`mutate`; bubbles through `mergeSlices` via the SAME `inherit()` helper `body`/`query` already use.
  `findTodo`/`patchTodo`/`dropTodo` declare `params: todo.zodSchema.pick({id:true})` — the id column's nanoid
  format/description/example, defined once, becomes both the runtime validator AND the doc's path-param schema.
  **ENFORCED, not just declared**: `sulukRoute`'s handler parses `c.req.param()` against it before `run` ever
  sees the input — a malformed id is a typed 400, never a silent pass-through or a 500.
- **`MergedInput<Params,Body>`** computes the flat `{...params,...body}` shape the runtime actually builds
  (`patchTodo`'s query now destructures `{id, ...patch}` from ONE flat input, not a hand-nested `{id,patch}`).
  **Merge-order hardening** (security-adversary finding, fixed): params now always wins over a same-named body
  key — the path is the caller's identity, a request body must never override it — regression-tested.
- **`InputOf<Fn>`** (mirrors `ReqOf<Fn>`) + **`passthrough`** let a controller type its `run` off the SERVICE it
  composes with, never importing the model's schema or writing `z.infer<...>` by hand — closing both the 2nd

## ✓ C106 — `sulukFmt.branch`/`race`/`quorum`: first-class branching, join policies, aggregation, graph I/O

Operator, quoting C105's own ADR back verbatim (*"It still is not a general conditional workflow engine... you
still do not have arbitrary branching, rich match/switch semantics, or a fully general control-flow language"*),
asked for four additions with a concrete type sketch: a first-class branch mechanism, a first-class join policy, a

(@≥0.85 design+build / @≥0.9 the matchEffect hang-bug + the verified sweep; burhan-converge clean, 79 files/480 claims).

- **A real, hang-causing bug was found DURING DESIGN, before any production code existed** — via a dedicated
  verification+critical-review pass (Ultracode workflow) BEFORE implementation, given the concurrency-correctness
  stakes: Effect has no built-in for either "any"/"quorum" join policy (`raceAll` races on first SETTLEMENT not
  first success; `firstSuccessOf` is sequential not concurrent), so both were hand-built via `Deferred`+`Fiber`. A

  `quorum<=0`, `quorum>`candidates) — all fixed with eager guards before forking anything.

  declared cases (never a general cross-graph executor). Cost aggregation is the MAX across cases (not sulukFmt/
  sulukFmt.all's SUM) — exactly one case runs per call. An earlier 3-generic-param signature defeated TS inference
  (a real bug caught via tsc); fixed by indexing `Out`/`R`/`In` off the `cases` object, mirroring `sulukFmt.all`'s

- **Deliberately still not built** (named honestly): a portable predicate/expression language, node-to-node

  result-projection rule distinct from `resultNode`/`output` — these need a genuine INTERPRETER evaluating
  predicate-shaped data against resolved runtime values, a categorically different, larger undertaking requiring
